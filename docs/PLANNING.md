# WhenWe 기획

팀원들의 학교 일정을 모아 **언제 다 같이 시간이 되는지** 찾아주는 서비스.

이 문서는 **무엇을 만들고 누가 맡는지**의 기준입니다. 다른 내용은 각 문서를 보세요.

## 1. 문제와 목표

팀 과제 회의 시간을 잡을 때, 7명이 각자 시간표·과제·시험 일정을 확인하고 단톡에서 조율하는 데 시간이 오래 걸립니다.
이미 LMS에 다 들어 있는 정보인데 사람이 옮겨 적고 있습니다.

**목표** — LMS 일정을 자동으로 모아 ① 다 같이 가능한 시간대를 한눈에 보여주고, ② 각자의 부담도까지 함께 고려해 회의 시간을 제안한다.

## 2. MVP (2일 안에 반드시 되는 것)

1. 로그인
2. LMS 일정 수집
3. 일정 정제 및 저장
4. 팀 생성 / 초대 코드 / 팀 참가
5. 개인 부담도 계산
6. 팀 여유도 계산
7. 팀 Heatmap 표시

**수집 방식 (현재 검증된 방식)** — 경기대학교 LMS에 **이미 로그인된 사용자 본인의 브라우저 세션**에서 Calendar HTML을 fetch해 파싱하고, 만들어진 일정 JSON을 서버로 보냅니다.

```text
브라우저   fetch → 파싱 → 일정 JSON  ──API──▸   서버   정제 → 저장 → 조회
           (역할 1·2)                            (역할 3·4)
```

- **fetch와 파싱은 사용자 브라우저에서 실행됩니다. WhenWe 서버가 대신 수행하지 않습니다.**
- **정제부터는 서버에서** 처리합니다. 서버는 브라우저가 보낸 일정 JSON만 받습니다.
- 서버는 사용자를 대신해 로그인하지 않고, 학교 ID/PW를 받지도 저장하지도 않습니다 ([§3 제외 범위](#3-제외-범위-이번에-하지-않는-것), [CONTRIBUTING §9](../CONTRIBUTING.md#9-secret-관리)).

## 3. 제외 범위 (이번에 하지 않는 것)

| 제외 | 이유 |
|---|---|
| **학교 ID/PW 저장 · 서버 대리 로그인** | 아키텍처 결정. **후순위가 아니라 하지 않기로 한 것**입니다 |
| 알림 (푸시 · 메일) | 후순위 |
| 반복 일정 편집 | 후순위 |
| 모바일 앱 | 후순위 (웹 반응형까지만) |
| 다중 팀 비교 | 후순위 |
| 복잡한 CI/CD | 후순위 (2일 프로젝트) |

> **웹 반응형은 범위에 포함**하되 **완료 조건은 아닙니다.** 좁은 화면에서 레이아웃이 깨지지 않는 정도를 목표로 하고,
> 2일 일정을 고려해 [FEATURES](FEATURES.md) `F5`·`F6`의 완료 조건에는 넣지 않습니다.

## 4. 용어 — 부담도와 여유도는 다릅니다

| 용어 | 단위 | 뜻 |
|---|---|---|
| **부담도** | **개인** (이번 MVP) | 과제·시험이 얼마나 몰려 있는지. "이번 주 A는 바쁘다" |
| **여유도** | 팀 × 시간대 | 팀원 전원 일정을 합쳐 **그 시간대에 다 같이 모일 수 있는 정도.** Heatmap 한 칸의 값 |

두 값 모두 역할 7이 계산합니다. **API 필드명은 미확정** — 확정되면 [api.md](api.md)에 적습니다.

> **팀 단위 부담도는 이번 MVP 범위가 아닙니다.** §2 MVP 목록에도, [FEATURES](FEATURES.md) `F7`의 **완료 조건**에도 없습니다.
> `F7` 구현 범위에 항목은 남아 있지만 **완료 판정 대상이 아닙니다.** 여유가 있으면 함께 만듭니다.

## 5. 기술 스택

| 영역 | 사용 | 상태 |
|---|---|---|
| DB · 인증 | **Supabase** (Postgres + Auth) | 확정 |
| Backend | **Node API** | 확정 |
| LMS 수집 | **사용자 브라우저에서** Calendar HTML fetch · 파싱 · 일정 JSON 생성 | 확정 (실행 위치 확정, **디렉터리 미확정**) |
| 일정 정제 | **서버에서** 처리 — 브라우저가 보낸 JSON을 공통 스키마로 정규화 | 확정 |
| Frontend 프레임워크 | — | **미확정** (Frontend 담당 2인이 결정. 현재 설정은 `VITE_` 접두사 · CORS 5173) |
| 배포 | — | **미확정** (후순위) |

## 6. 사용자 흐름

```text
로그인
 → LMS 일정 수집          (본인 브라우저 세션)
 → 일정 정제 · 저장         (공통 스키마로 정규화)
 → 팀 생성  또는  초대 코드로 팀 참가
 → 팀원 일정 취합
 → 개인 부담도 · 팀 여유도 계산
 → 팀 Heatmap에서 가능한 시간대 확인
```

## 8. 데이터 개요 (**미확정 — 역할 4가 확정합니다**)

정규화 후 일정 하나가 갖는 최소 정보만 합의된 상태입니다. 테이블 설계는 아직 없습니다.

```text
사용자 · 팀 · 팀원(사용자↔팀) · 일정(정규화된 이벤트)
```

- 일정은 **시작·종료 시각 + 종류(과제/시험/수업) + 출처**를 갖습니다. 구체적 필드명은 미확정.
- DB는 snake_case, **API 응답은 camelCase로 변환**합니다 ([api.md](api.md) 공통 규칙).
- 계산 결과(부담도·여유도)를 저장할지 요청 시 계산할지 **미확정**.

## 11. 기능 의존성

```text
[직렬 — 이 순서가 깨지면 뒤가 전부 막힌다]

── 브라우저 ─────────────────────────────────────────────
① LMS 일정 수집 (역할 1·2)      fetch → 파싱 → raw 일정 JSON 생성
   │
   ▼  ============ [ Backend API 경계 ] ============
── 서버 ─────────────────────────────────────────────────
② 데이터 정제 (역할 3)           공통 스키마 변환
   → ③ DB 저장 (역할 4)
      → ④ 팀 데이터 조회 (역할 4)
         → ⑤ 개인 부담도 계산 (역할 7)
            → ⑥ 팀 부담도·여유도 계산 (역할 7)
                  │
                  ▼
── 브라우저 (화면) ───────────────────────────────────────
⑦ Heatmap 표시 (역할 6)          ⑥의 결과를 조회해 렌더링

[병렬 — 위와 무관하게 바로 시작 가능]
로그인 UI · 팀 생성 / 초대 코드 / 참가 화면 (역할 5)   ← Mock 데이터로 선행 개발
```

**가장 이른 병목은 ②의 공통 스키마입니다.** ①③⑤⑥이 모두 이걸 기준으로 작업하므로 **Day 1 오전에 먼저 합의**해야 합니다.
④의 응답 형태도 ⑦이 Mock을 만드는 전제입니다 — 정해지는 즉시 [api.md](api.md)에 적어주세요.

각 단계가 어느 기능(`F1`~`F7`)에 해당하는지는 [FEATURES.md 의존성](FEATURES.md#의존성)을 보세요.
